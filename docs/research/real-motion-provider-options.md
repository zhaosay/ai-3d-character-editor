# Real text-to-motion Provider options

Research snapshot: 2026-09-26. This note compares open text-to-3D-human-motion projects for the editor's real-motion Provider milestone. Sources are first-party project repositories, papers, and framework documentation. No motion model was installed or executed.

## Recommendation

Use the authors' **HumanML3D MDM checkpoint** as the first model to prototype behind the existing FastAPI HTTP boundary. MDM is the most direct match for caption-to-motion, has an author-maintained PyTorch implementation, an explicitly MIT-licensed code repository, and a published 50-step checkpoint download that the authors describe as roughly 40x faster than their original sampling setup. This recommendation is for a prototype, not a claim that it already yields production-quality previsualization actions.

The user's ComfyUI Python 3.12 environment currently has PyTorch 2.13.0 with `torch.backends.mps.is_available() == True`. The MDM repository's official `environment.yml`, however, pins Python 3.7.13, PyTorch 1.7.1, CUDA 11, and Linux x86-64 packages; the authors document Python 3.7 and do not provide an MPS setup. Therefore the existing runtime proves Apple MPS hardware access but is not a drop-in MDM environment. An MPS prototype would require an isolated compatibility port against current PyTorch and an operator smoke run. Keep it separate from ComfyUI's environment to avoid disrupting image/video generation. A CUDA deployment is more faithful to the published environment, but also requires a suitable CUDA host. Before distributing weights or using them commercially, verify checkpoint and HumanML3D data/model terms separately: the repository's MIT code license does not by itself establish rights for every downloaded model or training asset.

The important engineering cost is **retargeting**, not HTTP. These research systems generate a fixed dataset representation (typically HumanML3D's 22-joint motion representation), not tracks named for the user's imported Mixamo/VRM/custom rig. The editor currently maps bone names and normalizes declared coordinate units/up-axis, but does not solve arbitrary skeleton retargeting. A real provider therefore needs to decode the model representation into poses and fit those poses to the requested rig before returning `AnimationData`.

## Project evidence and integration contract

- `README.md` says the current local and HTTP backend action content is MOCK, and the backend README identifies `/motion/generate` as a procedural-template endpoint. The backend implementation imports `generate_tracks_planned` from `backend/motion_mock.py`; it does not call a motion-generation neural model.
- `src/services/motion/types.ts` defines `MotionRequest` with prompt, skeleton snapshot, requested duration/FPS, stage props/interactions, and optional planned segments. `HttpMotionProvider` sends `prompt`, `duration`, `fps`, semantic-to-rig `bones`, rest transforms and rest positions, a rest-local skeleton hierarchy, seed, scene context, and planned segments to `POST /motion/generate`. The FastAPI request schema now accepts this richer skeleton payload, but the template generator does not consume it yet.
- The response is validated as `AnimationData` with named tracks and position/rotation/scale keyframes. A result only counts as REAL when `meta.source === "real"`. The client already supports `meta.bone_mapping`, `meta.motion_space` (right-handed Y-up/Z-up and m/cm/mm), and duration/FPS retiming.
- The model's caption-to-motion task is not automatically scene-aware. `scene_context`, contact constraints, stage props, obstacle avoidance, and action-segment isolation must remain editor-side planning/validation responsibilities unless a model explicitly supports them. A generated motion must not be reported as a physically valid interaction merely because model inference succeeded.

## Suggested implementation boundary

Keep the browser contract unchanged and add a backend adapter/worker rather than loading a research model in the browser:

1. The planner turns the user's request into ordered action segments. For the first prototype, call MDM once per segment using that segment's clause and requested duration; keep the existing scene/action validator responsible for timing, object reach, collision, support, and contacts.
2. Pin a model commit, exact checkpoint, dependency lock, and input/output representation. Expose readiness, queue/progress, cancellation/timeout, and a clear unavailable/error response. The current synchronous 120-second HTTP timeout is not a queue protocol; use a job endpoint if model load or generation can exceed it.
3. Decode the model sequence to canonical joint poses. Establish coordinate axis, units, root-motion policy, joint order, rest pose, and frame timestamps explicitly. Do not infer these from track names.
4. Add a retargeting stage from canonical joints to the requested `SkeletonSnapshot`: estimate local rotations against each target bone's rest direction/length; fit root displacement and scale to the character; preserve floor contacts where possible; and emit warnings for missing/ambiguous joints or poor fit. Name returned tracks with request bone names or report `bone_mapping`.
5. Return `source: "real"`, a truthful provider/model id, `motion_space`, and a stable segment breakdown. Use existing validation, time retiming, undo/redo, and collision re-scan. Do not call a template fallback "real"; on model unavailability, either keep the previous preview and show the failure or explicitly use the existing MOCK path with its honest label.

## Acceptance gate before marking Provider #5 complete

- Exact checkpoint and code revision are reproducibly obtainable, and checkpoint/data rights are documented for intended use.
- Run real inference for at least one prompted action on a real imported character. Confirm non-empty, correctly timed tracks bind and visibly move the character; verify local-vs-world transform conventions and root translation.
- Test a second skeleton naming convention, missing joint mappings, duration mismatch, invalid units/axis, model timeout/offline state, and undo/redo after segment replacement.
- Use at least two locally relevant prompts, including one multi-segment action; inspect for frozen joints, implausible floor penetration/sliding, and large discontinuities at segment joins. The model is a motion prior, not a physics/contact solver.
- Record inference latency and memory on the actual selected machine. Until MDM is ported and run end-to-end on the user's MPS runtime, keep MPS explicitly unverified; do not treat the existing ComfyUI PyTorch install as a compatible MDM runtime. CUDA requires a separate compatible host.

## Confidence and open questions

MDM remains the closest task match, but its published environment is substantially older and CUDA/Linux-specific compared with the user's MPS-only Mac runtime. The local PyTorch MPS availability does not establish MDM compatibility. The claims above do not establish output quality for Chinese prompts, interaction with props, combat choreography, or a specific imported character. Exact checkpoint licensing, current hardware memory demand, an isolated PyTorch compatibility port, Apple MPS operator coverage/performance, Chinese caption quality, and retargeting quality remain open and must be resolved by a small reproducible prototype before the Provider can be considered complete.

## Local machine probe (2026-09-26)

- ComfyUI's existing `.venv` is Python 3.12.14 with PyTorch 2.13.0 and reports `torch.backends.mps.is_available() == True`. Ollama currently lists `qwen3.5:9b` and several larger/smaller models. No MDM motion checkpoint was found among ComfyUI's local model files; its installed SDXL animation LoRA and video models do not provide named skeletal tracks.
- A direct `qwen3.5:9b` JSON keyframe prompt for an in-place right-hand wave returned parseable semantic Euler curves after increasing the token budget from an intentionally constrained first probe. The result raised the arm but produced only one brief hand-angle change rather than repeated wrist oscillation. This is evidence that a general chat model can emit a schema-shaped pose draft, not that its output is a reliable motion prior. It was not connected to the editor or judged on a real character, so it does not pass the Provider acceptance gate.
- Avoid labeling arbitrary LLM-authored joint angles as a successful animation Provider until a repeatable prompt contract, motion-quality check, rig binding, and visible playback have been demonstrated. The current tested AI role remains action planning; track synthesis remains MOCK.
