# 动作真实度：诊断与开源参考

## 一、诊断结论

对着开源动作库与运动原理逐条比对，原有 `schedules()` 的问题不是"模板数量少"，而是**生成的曲线不具备真人的运动特征**。逐项如下：

| 问题 | 原实现 | 真人规律 | 现状 |
|---|---|---|---|
| 步态周期 | `2*t` 硬编码，每段固定 2 步 | 周期应由步幅/腿长推导（0.4–0.7s/步） | ✅ `gaitPeriod()` |
| 膝关节 | `max(0, -18*sin)`：单向半波，只会朝一个方向弯 | 摆动期**先快速屈膝、再伸膝落地** | ✅ `gaitLeg()` 摆动段 |
| 髋部起伏 | 走路时完全没有 | 2× 步频；双支撑相最低 | ✅ 根位移叠加（末段淡出保证连续） |
| 骨盆旋转 | `spine` 仅 3° 前后倾，**无左右扭转** | 骨盆与胸廓反向旋转（走look核心辨识特征） | ✅ `hips`/`spine`/`chest` 组合 |
| 手臂 | 0.6× 正弦摆幅、肘完全伸直 | 摆臂时肘始终微屈(15–25°)，与同侧腿反相 | ✅ `armSwing`/`elbow` |
| 预备动作 | 所有模板直接起动 | Anticipation：先反向蓄力再发力 | ✅ `anticipationEnvelope()` |
| 跟随/回弹 | 无 | Follow-through：到位后轻微过冲回落 | ✅ 同上（overshoot） |
| 关节时序 | 肩肘腕同步 | 近端先动（肩→肘→腕延迟） | ✅ `proximalDelay()` |
| 呼吸耦合 | 仅 breath 模板，正弦单频 | 0.25Hz 胸廓起伏带动肩与头 | ✅ `breathSignal()` |
| 骨盆静止 | 站立/行走时绝对静止 | 骨盆从不停止（"假人感"主因） | ✅ 步态 bob |

## 二、参考的开源方案

本轮**没有引入外部依赖**，而是按以下开源项目总结的原理自行实现（`src/core/motion/gaits.ts`）：

- **[posers](https://github.com/thomasdavis/posers)** — VRM 人形程序化运动引擎。明确列出四条核心原则：
  1. Phase Envelopes（相位包络）而非状态机
  2. Maximum Bone Engagement（尽可能多的骨骼参与）
  3. **Anticipation + Follow-through**（预备与跟随）
  4. **Proximal-to-Distal Timing**（肩→肘→腕）、**Breath Coupling**（呼吸耦合）
- **[avatar-stage](https://github.com/rana-jatin/avatar-stage)** — Three.js 人形程序化动画库。强调 idle 行为（自动眨眼、呼吸、头部微摆）与 addable 叠加。
- **[CMU Graphics Lab Motion Capture Database](http://mocap.cs.cmu.edu)** — 免费商用动捕库，是步态相位、摆臂幅度的**权威参考数据**。本项目的 `gaitLeg()` 支撑/摆动期划分（60%支撑/40%摆动）即按此校准。
- **[three.js webgl_animation_walk](https://github.com/mrdoob/three.js/blob/dev/examples/webgl_animation_walk.html)** — 参考其 `ACESFilmicToneMapping` + HDR 环境的写实预览思路（已用于本项目写实预览面板）。

## 四、足部锁定（Foot Lock）

程序化步态的固有缺陷是**脚打滑**：支撑腿的脚本应钉在地面，但骨骼只是按曲线旋转，脚会随身体平移。

实现见 `src/core/ik/footLock.ts`（纯状态机）+ `src/services/motion/footLockRuntime.ts`（运行时）：

- **状态机**：触地 → 记录世界落点（plant）；持续触地 → 保持落点；离地 → 释放
- **每帧**用现成的两骨 IK（`applyIKChain`）把支撑脚拉回落点
- **实测脚底偏移**：脚骨原点≠脚底，且刚性蒙皮下网格是骨骼的兄弟节点而非子节点，
  故用 `skeleton.bones.indexOf(foot)` 定位绑定网格后扫描顶点实测，**不能硬编码常数**
- **安全降级**：漂移超过 `maxCorrection`（IK 追不上）时放弃本落点重记，避免腿被拉变形；
  时间回退（拖时间轴）自动重置状态；速度异常（时间跳变）重置落点
- **Scrub 从 0 重放**：落点状态是时间累积量，直接在目标时间求解会与播放不一致，
  故暂停拖动时从动画起点逐步重放

实测效果（程序化男角色走 3 秒，见 `tests/footLock.integration.test.ts`）：
**支撑脚水平漂移从 ~70cm 降到 ~1.7cm（约 40 倍）**。

UI：右侧「写实预览」面板底部，默认**关闭** —— 手工摆过脚部关键帧的动画会被它覆盖。

## 五、台阶/斜坡地面投射

足部锁定原本只有水平方向，落在平台上会浮空或入地。新增 `src/core/world/ground.ts`：

- **解析高度场**（不做 raycast）：基准平面 + 若干可站立盒（台阶/平台/床/桌椅）
- 采样 `(x, z, originY)` → `{height, normal, source}`，用**探测窗口**限制搜索范围
  （`[originY − probeDown, originY + probeUp]`），避免把远处高台"吸"上来
- 重叠盒取最高顶面；支持 yaw 旋转的水平投影判定
- UI：写实预览面板里可增删台阶、调高度与 Z 位置

> **尚未支持从场景道具自动构造高度场。** 曾有一个 `groundFieldFromProps()`，但验证发现它把道具的
> **整体顶部**当作可站立面，对 chair/sofa/room 全是错的（默认椅偏差 +43cm，room 会把角色抬到墙顶 3m），
> 且只被自己的单测调用、从未进入运行时，故已删除。道具表面的正确约定（chair 座面 `0.48h+0.04`、
> sofa `0.58h`、table/bed 顶面 `h`）需要在下一轮与 `world.ts` / `collision.ts` / `scenePlan.ts`
> 三处已有的常数一起统一后再实现。

## 六、动作体检：用项目自己的物理分析器找问题

项目已有物理分析器（`core/physics/analyze.ts`：穿地 / 脚滑 / 加速度尖峰 / 平衡 / 关节极限）。
用它对全部 24 个模板 × 男女做了体检，并补了它缺失的**悬空**与**躯干穿透**两类检查。

### 先修测量工具：穿地数值此前系统性偏小

`collectTrajectory` 读的是**脚骨原点**（踝/跟处），比可见脚底高约 15mm；脚旋转后偏差更大
（鞋底盒会转向，静态偏移完全失效）。已改为按**绑定网格的真实最低顶点**判定。
验证：脚俯仰 34° 时，现在报 0.003m = 真实脚底（旧代码会报 0.019m，低估 16mm）。

### 体检暴露的问题（原有检测器完全看不见）

| 动作 | 症状 | 归因 |
|---|---|---|
| `sit` 坐地面 | 臀下悬空 **0.871m**，91/91 帧 | 模板层：根骨位移 key 数 = 0 |
| `orient` 侧卧 | 终态仍悬空 **0.553m** | 模板层：同上 |
| `lie` 落地 | 穿地 **0.425m** | 模板时序 + 分支判据 |
| `sleep` 单独使用 | 前 2.0s 悬空 0.873m | 根骨下降时序 |
| `kneel` | 全身最低 0.228m，无一处触地 | 硬编码 `toOffset=[0,-0.42]` 不足 |
| 道具穿透 | 骨盆入床垫 0.167m 等 22 组 | 接触层缺高度 |

**第二个检测器同样看不见悬空**：`collision.ts` 的胶囊扫掠只测穿透、从不测"缺少支撑"，
在 `sit`/`kneel`/`orient`/`sleep` 上实测 findings = 0。

## 七、本轮修复（含实测结果）

| 修复 | 前 | 后 |
|---|---|---|
| `lie` 穿地（两条独立原因） | **0.425m** | **0.000m** |
| `sit` 臀下悬空（无支撑面） | 0.871m | **0.16m** |
| `sit` 脚穿地 | — | 开启足部锁定后 **0.000m** |
| `orient` 髋部下沉 | 0（恒静息高） | 0.854m |

### `lie` 的两个根因

1. **时序错配**：髋部位移包络在段长 65% 完成，旋转包络 100% —— 腿还没转平，髋已降到底。
   子代理反事实验证：只同步包络，穿地从 −0.425m 降到 −0.129m（消掉 70%）。
2. **分支判据错误**：`groundedFall` 靠子句正则 `/地面/` 选择，导致英文 `"lie down"` 走
   else 分支 —— 拿「已经躺好」的直腿（thigh −8°/shin 0°）配「站立离地 13cm」的髋高。
   改为按**有无支撑面**判定（`onBareGround`）后，中英文穿地都归零。

同步包络时踩到一个坑：倒地编排（先屈膝 169° 再伸直）需要**延后**下落，否则会出现
"膝还弯着但髋已到底 → 脚插地 0.138m"。最终按编排分支分别处理，并被
`tests/worldActionPlan.test.ts` 的既有碰撞断言覆盖。

### `sit` 的坐姿分层

坐地面与坐椅子需要**不同的腿折叠**：椅姿（thigh −72°/shin +68°，脚垂直落地）用在地面上会让脚
插地 0.649m。改为按 `onBareGround` 用盘腿角度，剩下的 0.49m 残余交由足部锁定兜住
（验证：开启后降至 0.000m）—— 这正是「模板给姿态语义、接触层给世界坐标」的分工。

## 八、坐椅姿态：髋目标按座面推导

`resolvePropInteractionFrame` 原来用 `height * 0.74` 魔数算坐姿髋目标，关节抬升 **0.194m**；
而 bed(+0.12) / sofa(+0.126) 都是 ~0.12~0.13（骨盆代理半径 0.13）。**椅子是离群值**，
导致角色坐椅时骨盆网格**悬空 8.1cm**（可见），且旧魔数在合法椅高范围 [0.2, 3.0] 内
摆幅达 72.8cm（h=0.2 时坐进座面 10cm）。

改为按**真实座面几何 + 骨盆半径**推导：`0.48h + 0.04 + 0.13`。实测：

| 体型 | 悬空（前） | 悬空（后） |
|---|---|---|
| male 默认 | +8.11cm | **+2.53cm** |
| female 默认 | +6.65cm | **+1.07cm** |

且对椅高**完全免疫**（旧值在 h=0.2~3.0 摆幅 72.8cm，新值恒定）。
`inspectPropSupportWarnings` / `inspectGroundSupportWarnings` 零变化。

### 顺带修掉的声明面错误

椅面被 4 处声明为 `0.52h`，真实是 `0.48h + 0.04`（座板盒几何），误差 `0.04(1-h)`：
椅高 0.2m 时差 3.2cm、3.0m 时差 8cm。已统一为真实几何
（`world.ts` 的 `propInteractionWorldPoint` 与 handTarget、`collision.ts` 的 surface 与
期望接触带、`scenePlan.ts` 的 surface 与 likelyRanges）。

> **注意**：这类"声明面 vs 真实几何"的偏差本身不会被任何现有检查发现 ——
> `inspectPropSupportWarnings` 的判定带 `gap ∈ [-0.08, +0.16]` 足够宽，能同时容忍
> 旧魔数造成的 8cm 悬空和正确值。所以本项是靠人工核对几何算式发现的，不是检测器报出来的。

## 十、坐姿按座高反解（已修，实测数据）

### 问题根因（三处，缺一不可）

`sit` 模板原先用**固定欧拉角** thigh −72° / shin +68°，这个角度只对**一个**座高成立：

| 缺陷 | 说明 |
|---|---|
| 腿角固定 | 不随座高缩放，椅子/高凳/地面必然有一个错 |
| 座高固定 16cm | 骨盆半径被写死，与实际座面无关 |
| 髋俯仰 38° | `sitSolve` 的闭式解以「髋不俯仰」为前提，加上会让脚底再陷 10cm |

### 做法

`src/core/ik/sitPose.ts` 从**真实骨架**量出连杆（大腿/小腿长、髋高差、鞋底高度），
再按**实际座面高度**反解两骨角；髋高用同一解的跨距反算，保证角度与位移同源。

关键细节（都是实测踩出来的，不是推导出来的）：
- **鞋底高度必须实测**（`measureSoleDrop` 取绑定到脚骨的网格最低顶点，实测 1.47cm）。
  拿脚骨原点 y 当踝高会引入 4cm 系统误差。
- **有解时髋俯仰必须为 0**，改用 spine 前倾 18° 表达坐姿前倾（实测 0.0037 → −0.099）。
- **无 legChain 时保持旧行为**（髋落在座面），不凭 16cm 魔数把骨盆悬空。
- 地面盘腿是**平面两连杆表达不了**的姿态（解算器会给出「劈腿」解 thigh −147°），
  故 `onBareGround` 时不走解算器，保留专门的盘腿角度。

### 实测结果（内置示例角色，脚底离地量）

| 座面高度 | 修复前 | 修复后 |
|---|---|---|
| 0.40m | −42.3cm（插地） | −0.5cm |
| 0.45m | −37.3cm | −0.4cm |
| 0.50m | −32.3cm | −0.4cm |
| 0.60m | −22.3cm | −0.2cm |
| 0.62m | −20.3cm | −0.2cm |

原先文档记的「28.2cm」是用 `inspectMotionCollisions` 的骨段近似算的；
用**绑定网格最低顶点**实测是 20~42cm（随座高变化），修复后 < 0.5cm。

### 真人动作库（Quaternius CC0）的实测结论

读 `humanoid-v1.json` 内的真实 GLB（10 clip / 159 通道 / 30fps）：

- **行走、慢跑、蹲着前进的根部位移均为 0.0000m** —— 这些是**原地踏步**动捕。
  所有骨骼的 translation 轨道全程恒定（绑定姿态偏移），只有旋转在动。
  因此「从源 clip 提取根位移再缩放」（stride-fit）**没有数据可提**，未实现。
- 可用的节奏参考：行走 1.333s/周期（**45 步/分**）、慢跑 0.933s（**64 步/分**）、
  大腿摆角 61.8° / 96.6°。注意 45 步/分**明显低于**真人步行（约 100–120 步/分），
  直接照搬并不会更真实。
- 唯一带真实位移的是「坐下」（水平 0.336m + 垂直 0.245m）与「站起」（反向）。

## 十一、蹲/跪按腿角反解髋高（已修）

### 问题根因

与坐姿同源：`squat` 写死根骨位移 `-0.32`、`kneel` 写死 `-0.42`。
写死的米数只对**一个**身高成立，角色一换体型就错。

### 实测（内置示例角色，脚底离地）

| 身高 | squat 前 | squat 后 | kneel 前（脚底） | kneel 前（膝高） | kneel 后（膝高） |
|---|---|---|---|---|---|
| 1.65m | −8.0cm | **−0.6cm** | +33.0cm | 0.257 | **0.113** |
| 1.75m | −4.7cm | **−0.6cm** | +37.7cm | 0.298 | **0.120** |
| 1.95m | −1.5cm | **−0.6cm** | +47.0cm | 0.380 | **0.133** |

注意 kneel 的错误**随身高线性增长**（33→47cm），而 squat 的插地**随身高缩小**
（−8.0→−1.5cm）—— 两者都是「固定米数撞上不同腿长」的同一症状。

### 做法与实测细节

- 新增 `hipHeightForWorldAngles`：给定**任意**世界前倾角反解髋高（`sitSolve.ts`）。
  坐姿用的是「解算出的角」，蹲/跪是「人为选定的角」，但都需要髋高与腿角自洽。
- 新增 `hipHeightForKneel`：跪姿的接触面是**小腿/膝**而不是脚底。
  解剖上跪地时膝盖与小腿前侧着地、脚背朝后翘起，**脚底离地二十几厘米是正确的**。
  用脚底当接触面会得出悬空的脚 —— 这正是原来 20~47cm 悬空的来源。
- **世界前倾角必须实测**（含髋俯仰贡献，局部角 ≠ 世界角）：
  蹲 = hips 28°/thigh −78°/shin +92° → 世界 thigh **50°**、shin **−42°**；
  跪 = hips 28°/thigh −92°/shin +169° → 世界 thigh **64°**、shin **−75°**；
  扶地跪 = hips 66° → 世界 thigh 26°、shin −37°。
  猜错这几个角会让髋沉到地面以下（实测 hips.y = −0.012）。
- 无 legChain 时退回旧魔数，不凭猜的骨长造新误差。

### sleep 单独使用

实测已正常：`planClauses('睡觉')` 会自动规划 `lie` → `sleep` 两段，
单独传 `sleep` 模板时终帧 hips.y=0.130、全身最低点 0.0030（贴地）。
原先「躺着悬空再落下」的问题已被早前的 `groundedHipOffset` 处理覆盖。

## 十二、走路步幅/步频随体型缩放（已修，附文献依据）

### 问题

`march` 模板把 `legLength: 0.85, stride: 0.62` 两个值**写死在两处调用点**，
真实腿长从未传入。实测（内置角色，4s 走路）：

| 身高 | 实测腿长 | 修复前总位移 | 修复前步频 |
|---|---|---|---|
| 1.65m | 0.841m | 0.880m | 112 步/分 |
| 1.75m | 0.892m | 0.880m | 112 步/分 |
| 1.95m | 0.994m | 0.880m | 101 步/分 |

腿长差了 18%，位移却完全一样 —— 高个角色用同样的位移配更长的腿，
只能走出**更密更短的碎步**。

### 文献依据

- Takahashi et al.（最优行走的代谢最优）：`SL_opt = 0.781·L`、`SR_opt = 138.5·L` 步/分、
  髋关节角约 46°。
- KJAB 对 50 名成人（腿长 0.89±0.05m）实测：单步 0.62m、步频 109.8 步/分，
  即**步幅/腿长 ≈ 0.70**。
- 几何相似摆的结论：步频 `SR ∝ 1/√L`（不是 ∝ L），所以腿越长单步越慢、频率越低。

据此取 `STRIDE_PER_LEG = 0.74`（0.70~0.78 居中）。

### 修后实测

| 腿长 | 步幅 | 周期 | 步频 | 步速 |
|---|---|---|---|---|
| 0.80m | 0.592m | 0.485s | 124/分 | 1.22m/s |
| 0.85m | 0.629m | 0.500s | 120/分 | 1.26m/s |
| 0.89m | 0.659m | 0.512s | 117/分 | 1.29m/s |
| 1.00m | 0.740m | 0.542s | 111/分 | 1.36m/s |

符合真人规律：**高个步子更大、频率更低、速度更快**。

### 顺带修掉一个采样混叠 bug

修周期时暴露出来的既有问题：关键帧网格 `STEP = 0.25s`，而步态周期约 0.5s ——
**正好 2:1**。按 0.25s 网格采样每次都落在步态的同一相位，
髋部起伏 `hipLift` 被整段抹平成常数（实测 spread = 0.00000，看起来像溜冰）。

之前没暴露，是因为旧的 `gaitPeriod` 返回 0.507s（略微偏离 0.5），
混叠被"不精确"意外打破。周期取整后问题立刻显形。

修法：走路模板用更细的关键帧网格（`min(STEP, 周期/24)`，约 1/60s），
其余模板保持 0.25s 不变（不必无谓增加关键帧数）。
实测走路关键帧 17 → 193 个，髋部起伏 spread 0.00000 → **0.044**（2× 步频完整保留）。

## 十三、床上躺卧的多点接触（已修）

### 先纠正一个测量错误

最初测出「背悬空 37.1cm、头悬空 103.7cm、腿穿插 −49.7cm」，
据此准备按「背/头/腿同时贴床」做多点接触。**这三个数字全是测量假象**：

`THREE.SkinnedMesh` 的 CPU 端 `matrixWorld` **不包含骨骼变换** ——
蒙皮是在顶点着色器里做的。用 `matrixWorld` 直接变换顶点等于假设角色没变形，
于是量到的是未变形的站姿几何。

正确做法是手工构造蒙皮矩阵：

    skinMatrix = Σ w_k · bone_k.matrixWorld
    worldVertex = bindMatrix⁻¹ · skinMatrix · localVertex

改对之后真实基线是：**背 +9.6cm 悬空、头 −8.2cm 穿床板、腿 +3.4cm**。
（此前 `inspectMotionCollisions` 用骨段近似，与此口径不同，两者不可直接比较。）

### 根因

`lie` 把髋骨放到 `liePosition`（= 床面 + 0.12m 的魔数），
但一个高度不可能同时贴合背/头/腿三个厚度不同的部位。

### 做法

新增 `src/core/ik/restContact.ts`：

- `lowestByGroup`：按接触组量蒙皮顶点世界最低 Y（真·CPU 蒙皮）
- `measureRestContact`：量「各组最低点相对髋骨」的偏移
- `hipHeightForContact`：由偏移反解根骨高度
- `supineContactOffset`：生成阶段用的几何估计（按 `hipDrop` 线性缩放）

**以背/臀为锚点**，而不是全身最低点 —— 仰卧时躯干才是承重面；
若用全局最低点（实测是头，比背低 0.18m）会把整个身体抬高 16.6cm，反而更糟。

### 顺带修正躺姿本身

- **头部角度**：原来 `head: −8°`（低头）。实测扫描发现负 X 角把头**往床板里压**
  （−8° → 低于背 20cm，−20° → 54cm），正 X 角才抬离床面。
  仰卧中立位应为 `0°`（实测头比背高 3cm）。
- **腿部角度**：`thigh −8°` 已接近最优（越负越往下穿），保留。

### 结果（内置角色，相对床面）

| 身高 | 背 | 头 | 腿 |
|---|---|---|---|
| 1.65m | −0.7cm | +4.4cm | −6.3cm |
| 1.75m | −0.2cm | +5.2cm | −6.3cm |
| 1.95m | +0.9cm | +6.7cm | −6.2cm |

床面高度 0.35 / 0.5 / 0.62m 三档下**接触偏移完全一致**（−0.7 / +4.4 / −6.3），
且身体绝对高度精确跟随床面（髋骨恒在床面上方 2.4cm）—— 这正是「按接触解算」应有的表现。

头高于床面、踝低于床面是**正确的解剖结果**（颅顶在背上方、直腿时踝悬于床沿），
不应强行拉到同一平面；测试按组分别设界。

## 十四、躺卧过渡期的逐帧剖面（记录现状，含未修缺陷）

终帧已由多点接触对齐（第十三节），但**过渡中途**是另一回事。
实测剖面（内置角色，床上躺下 3s，相对床面 cm）：

```
t(s)   0.0  0.3  0.5  0.8  1.0  1.3  1.5  1.8  2.0  2.3  2.5  2.8  3.0
背    136  135  132  126  117  104   88   70   51   33   17    5    0
头    262  261  257  249  233  210  179  143  104   66   34   13    5
腿    -48  -49  -51  -53  -53  -50  -45  -37  -27  -17   -9   -5   -6
```

背与头单调下降、全程不穿床板，终帧精确回到接触高度。
但**腿在 t≈1.0s 穿地 3.0cm**（腿相对床面 −53cm，床面 0.5m）。

### 为什么没修

根因是结构性的：`lie` 模板是**绕髋的刚体旋转 + 直腿**，
脚随身体转过一段圆弧，该圆弧必然扫过地面以下。靠调 `thigh/shin` 角度
无法消除 —— 试过给上床路径加预屈膝：

- 实测 thigh **正**角才抬脚（0°→0.033m、+12°→0.084m、+30°→0.228m），
  负角反而压低（与直觉相反，靠参数扫描确认）
- 加预屈膝确实把穿地从 5.3cm 降到 3.6cm，
  但同时**改变了躺姿终态的腿部角度**（终态腿相对床面从 −6cm 变 −23cm）

收益不抵副作用，故回退，未采纳。

真正解决需要二者之一：
- **逐帧对地 IK**：每帧解髋/膝/踝使支撑点贴面（开销高一档）
- **预计算「根高度 ~ 身体倾角」曲线**：先用真实骨架离线采样，
  生成后按曲线插值（成本在生成期，运行期几乎免费）

`tests/bedTransition.test.ts` 如实记录该剖面并锁定「不反弹/终帧对齐/不穿床板」
三条不变式，穿地一项只记录不断言 —— 它是已知缺陷，不是回归。

## 十五、24 个模板的系统体检（2026-10）

对 `KNOWN_TEMPLATES` 全部 24 个模板做量化体检（内置角色，2s 段）。
结论：**只有一个真实缺陷**，其余两处初判为误报。

### 体检项与结果

| 指标 | 结果 |
|---|---|
| 局部关节角越限 | **全部 24 个模板无越限** |
| 起始姿态偏离静息 | `wave` 偏离 **55°**（唯一缺陷） |
| 最大角速度 | 最高 `sword` 501°/s、`block` 316°/s、`kick` 298°/s |

### 误报更正（重要）

**1. 用世界四元数测关节角是错的。** 初版审计把每根骨的世界旋转与静息比，
报出 `orient` 8 个关节 103°、`lie` 手部 148° 等。改测**局部**旋转后全部归零。
真相是：髋转 90° 时所有子骨的世界朝向都跟着转 90°，那是**继承的父旋转**，
不是该关节本身超限（转髋不会让脊椎反弓）。`JOINT_LIMIT_DEGREES`
应作用于局部角，不能作用于世界角。

**2. 高角速度不是缺陷。** 初判 `sword` 501°/s「过快=抽搐」，查文献后撤回：

| 关节 | 真人实测峰值角速度 |
|---|---|
| 肩（拳击后手勾拳） | 1069 ± 105 °/s |
| 肘伸展（职业拳手） | 651 ~ 2363 °/s |
| 躯干旋转（后手直拳） | 270 ± 71 °/s |

我们 501°/s **低于**真实出拳速度。发力类动作本来就该快 ——
`anticipationEnvelope`（蓄力 14% + 快速出剑）是符合运动科学的。

### 真实缺陷：wave 从不回到静息

原写法 `55 − 20·sin(...)` 是**常量偏置 + 振荡**，手臂永远停在 35~75°，
从不放下。实测第 0 帧就偏离静息 **55°** —— 挥手应该从站立姿势起手。

改为「抬臂包络 × 摆动」：前 25% 抬起、中间保持、末 25% 放下。

| | 起始 | 峰值 | 结束 |
|---|---|---|---|
| 修复前 | 55° | 75° | 55°（一直举着） |
| 修复后 | **0°** | 76° | **0°** |

实测曲线：`0→20→38→48→53→62→71→76→61→29→0`（度）。

## 十六、动画交叉淡化与状态机骨架

### 之前的问题

切换动画只有一条路径：`selectAnimation(id)` → `currentTime = 0, playing = false`，
即**硬切**。走路 → 停步时角色瞬间弹回站立姿势，看起来像滑块而不是人。

全仓库搜索 `crossfade|blend|transition|state machine` 只找到道具挂载的
`position.lerp / quaternion.slerp`（stage prop，非动画），**动画之间零混合**。
`THREE.AnimationMixer` 只在 `motionRetarget.ts` 用作一次性离线烘焙器，
从不调用 `fadeIn/fadeOut/crossFadeFrom/weight`。

### 核心：blendPoses

`src/core/animation/crossfade.ts`。

**关键陷阱：骨骼集合不匹配。** `sampleAnimation` 只为轨道里出现的骨骼产出条目，
某通道无关键帧时整个通道被省略（retarget 产物就是 rotation-only）。
若直接「先应用 A 再应用 B」，只属于 A 的骨骼会**沿用 A 的旧值**，
表现为淡化过程中某些骨突然弹一下。

因此混合必须取**骨骼名并集**，缺失通道用**静息**兜底
（`SkeletonSnapshot.nodes[].restLocal`，经 store 的 `restOf()` 提供并按节点集缓存）。

- 旋转：slerp（球面插值，不是分量线性）
- 位置/缩放：lerp
- 面部 morph：线性，缺失侧视为 0；**0 值必须写入**才能覆盖上一个动画的表情
- 权重曲线：smoothstep（`fadeWeight`），避免线性过渡的机械感

### 状态机骨架

`src/core/animation/stateMachine.ts`，采用 Unity Animation Controller 的模型：

| 概念 | 我们的实现 |
|---|---|
| Entry | `def.entry` |
| Any State（强制打断） | `from: ANY_STATE`，受击/死亡可打断任何动作 |
| 触发器 | `trigger` 参数名 + `triggerValue` 极性 |
| 退出时间 | `exitTime`（归一化 0..1，不依赖 clip 绝对时长） |
| 过渡时间 | `duration` = 交叉淡化时长 |

**比 Unity 多的一处**：加了 `triggerValue`（默认 true）。
Unity 的 bool 触发器只能表达「变为 true」，但**停步天然是「isMoving 变 false」**，
没有反向极性就无法表达「走路 → 站立」。

打断**不等退出时间**（正在挥拳时挨打，不该等拳挥完）。
淡化中再次被切换时**保留当前淡化进度**而不是重置。

### 落地

- store：`fadeFromId / fadeFromTime / fadeElapsed / fadeDuration / transitionDuration`，
  新增 `transitionTo()` / `tickFade()` / `cancelFade()` / `blendedPoseAt()` / `fadeWeight()`
- 播放循环 `PlaybackEngine`：帧循环与 ScrubApplier **两处都要用 `blendedPoseAt()`**，
  否则拖时间轴会跳回硬切结果
- 时间轴 UI：下拉切换即交叉淡化，旁边「过渡」输入框调时长（0 = 硬切）

### 测试

`crossfade.test.ts`（14）纯函数边界、`stateMachine.test.ts`（17）状态机语义、
`crossfadeIntegration.test.ts`（9）经 store 的真实生命周期
（开始 → 推进 → 中间姿态确实是混合 → 结束自动丢弃来源）。

## 十七、PBR 材质面板（新增）

### 之前的空白

项目里**没有任何材质面板，也没有任何贴图加载**：
- `loadGltf.finishLoaded` 只统计材质数量（`materials++`），**从不触碰 material 属性**
  —— 导入 GLB 后用户改不了金属度/粗糙度/贴图
- 内置角色只有 `Appearance.skinRoughness` 一个标量（0.25~0.85）
- 全仓库搜 `TextureLoader|createImageBitmap|material.map|normalMap` 零命中；
  `createObjectURL` 全是下载链接，`FileReader` 只用于 AI 分镜 PNG

### 顺带修掉一个真 bug

`collectThemedMaterials` 只收 `isMeshStandardMaterial`，而 **MeshPhysicalMaterial 继承
MeshStandardMaterial 但标志不继承**。内置示例角色的皮肤恰好是 `MeshPhysicalMaterial`
（带 sheen 模拟皮脂），于是**换肤色对示例角色完全无效**。已改成两个标志一起判。

### 材质枚举按「路径」而非 uuid

uuid 是运行时随机值，**存取项目后就变了**。改用「root→mesh 子索引路径 + #材质序号」，
与 `core/face/morphs.ts` 的 `listMorphTargets` 同一套约定，覆盖才能存进 project.json 并正确恢复。

只存 diff 是不够的：清空覆盖后必须把材质**还原成 GLB 自带值**，
否则画面停在被改状态而面板显示「未修改」（滑块与实际不一致）。

法线/粗糙度/金属度是**数据**不是颜色，标成 sRGB 会让画面失真。
`DATA_TEXTURE_SLOTS` 显式区分，导入时按线性解读。

`loadGltf.dispose()` 此前只 dispose 几何体，材质与贴图一直占显存。已补上
（五类贴图 + 材质本身，按 uuid 去重）。

`pbr.test.ts`（19）枚举/反查/钳制/多材质/Physical 识别、

## 十八、双手持剑：局部摆动 → 全局约束（已修）

### 问题核实（先测量，不猜）

用户指出「拿剑姿势不对」。核实 `procedural.ts` 的 `sword` 模板后确认：

| 项 | 原状 |
|---|---|
| 主手 | `upperArm −115°`、`forearm −25°` |
| **副手** | **只有 `upperArm ±12°`，无 forearm** |
| 下肢 | **完全没有轨道** |
| 躯干 | `spine` 绕 Y `±28°` |

即：两只手不在同一把剑上，也没有站姿。这不是参数没调好，而是**只有局部关节摆动、没有任何全局约束**。

### 循环依赖陷阱（决定了方案形状）

剑的世界变换 = 主手 FK × `attachOffset`（`WorldStage.tsx:94-103`）。
若让**两只手都反向由剑决定**，就是循环依赖。良构分解是单向链：

```
护手规格 → 主手 IK（世界目标）→ 剑变换（FK 自主手）→ 柄尾锚点 → 副手 IK
```

主手只被护手规格驱动、不被剑驱动；副手只被剑驱动、不回写主手。
因此无论 `useFrame` 执行顺序都不成环，**也不需要给 R3F 加 `renderPriority`**。

### 剑锚点

`src/core/weapon/grip.ts` 的 `SWORD_ANCHORS` 对齐 `WorldStage.tsx` 的实际 JSX 几何
（握柄 cylinder 局部 y ∈ [−0.13, +0.05]）：

- 主手握点 `grip` 局部 `[0, −0.02, 0]`
- 副手握点 `pommel` 局部 `[0, −0.11, 0]`（双手间距实测 **90mm**）

剑长只影响刃尖，不影响握点 —— 换剑不脱手（已测）。

### 朝向：由解剖推，不靠「面朝 +Z」约定

先试了 `forward = normalize(shoulder − hips)`，**实测失败**：两肩与髋的水平投影
重合，该向量只剩侧向，`target.z == 0`，护手位跑到体侧。

改用右手系的解剖关系：角色左侧 = `up × forward`，故 `forward = left × up`。
「哪侧是左」是语义层已判定好的（`rigDetect` 的 L/R 识别），不是命名约定，
因此对任意导入骨骼成立。自检：demo rig `left=(1,0,0), up=(0,1,0)` → `forward=(0,0,1)` ✓。

### 体型自适应：为什么不用烘焙角度

实测把护手式 IK 解算后反读局部欧拉角，得到
`UpperArm_R=[-9.9,-0.2,2.6] Forearm_R=[-64.4,-31.4,48.2]`。
**这些数字只在 demo rig 的骨长上成立。** 本项目一贯体型自适应
（坐姿按真实骨长反解、步幅按腿长缩放），故护手位改为**以臂长归一化**的
`SwordGuardSpec`（`forward/inward/down` × 臂长），运行时 IK 解到具体骨骼。

护手位扫掠：78/80 的候选格点副手够得到柄尾，护手工作区很宽。

### 腕部定向：补上 `applyIKChain` 的已知缺口

`applyIKChain` **只解位置、不管末端朝向**（`applyIK.ts:45-46`），
而剑的世界朝向 = 手的世界四元数（`WorldStage.tsx:102`）。
于是刃向是手臂 IK 的**副产品**。实测 `STRIKE_SPEC` 下副手偏差 **139mm** ——
手臂伸展后手腕翻向不明，柄尾落到了够不到的位置。

解法在解剖上成立：**手腕本来就会转**。`aimHandBladeAxis` 只动 `Hand` 骨、
不动前臂，故手臂解出的位置不受影响。手腕不是球关节，故按真实活动度做
swing-twist 分解后分别钳制（摆动 ±60°、扭转 ±80°），达不到时返回**实际达成的**方向。

效果：副手偏差 **139mm → 58mm**。

### 出剑规格：原本物理上不可达

初版 `STRIKE_SPEC`（`forward 0.92`）实测：
柄尾离副肩 **630mm**，而副臂只有 **580mm** → `reached=false, clamped=true`。

这不是 bug，是**规格设计错误**：双手剑不能让主臂单臂伸直，两只手必须分担伸展距离。
扫掠 4×4×3×4 = 192 组后取可行解：

| 规格 | 主臂伸展率 | 副手柄尾偏差 | 刃向误差 |
|---|---|---|---|
| `GUARD_SPEC` | 0.811 | **13.5mm** | 43.7°（腕部受限） |
| `STRIKE_SPEC` | **0.881**（肘微屈不锁死） | **14mm** | **26.3°** |

另有 **100 组**可行解（伸展率 >0.85 且柄尾 <30mm），说明可行域不窄。

### 已知边界（诚实记录）

- **挥击弧线未解**。刃向从斜举到下劈需 **90~103°** 腕旋转，解剖上做不到。
  真实下劈靠肩+肘带动的弧线，不是手腕 —— 需要**带朝向的解析手臂 IK**，
  不是腕部钳制能补的。本轮交付的是「一组双手握持姿态」，不是挥击弧线。
- 柄尾偏差对刃向**不敏感**：刃向在 ±90° 范围内变化时 `offErr` 恒为 13~14mm
  （握持由臂长决定，不由剑指向决定）。
- `attachTo=null`（未持剑）与骨骼不完整时安全返回 `null`，不影响播放。

### 播放循环接线（原先的隐藏缺口）

三个既有求解器**都不在播放时运行**：`PlaybackEngine` 播放分支只做 FK、
`IKHandles`/`IKSolver` 有 `if (playing) return`、`ScrubApplier` 只在暂停时跑。
不接线的话副手在播放中永远握不住剑柄 —— 这是原始 bug 的成因之一。
故在 `applySampledPose` 之后接入 `solveHeldSwordGrip`（播放 + scrub 两处）。

### 下肢站姿

`sword` 模板补齐站姿：前脚承重约六成、膝微屈 20°、髋下沉、躯干侧向前脚。
开立量与髋下沉按腿长缩放（`scaleStanceToLeg`，基准腿长 0.86m）——
写死米数会让 1.6m 与 1.9m 的角色一个劈叉、一个没站稳。

### 一处测试断言的修正

`worldActionPlan.test.ts` 原断言交接后主攻臂偏转是副手的 `×2`。
**那个阈值编码的正是「副手近乎不动」的单手剑假设 —— 恰是本次修掉的 bug。**
双手握剑时副手同样在柄上、必然参与动作，实测领先幅度 1.19×。
改为断言「主攻臂领先」且「两条前臂都有明显运动量」。

`motion.test.ts` 的骨骼 fixture 补齐 `chest/hips/shin.L/shin.R/foot.L/foot.R`
（持剑模板现在真的用到躯干与下肢）。

1. **调用点在错误的生命周期里。** 原先挂在 `PlaybackEngine` 的 useFrame，

   静止看场景时两者都不满足，`solveTwoHandedGrip` 一次都不执行 ——
   现象是「播放时偶尔对、停下来看又松开了」。`ScrubApplier` 也救不了（只在暂停且时间变化时触发）。

   不用 `renderPriority`：R3F 里非 0 的 priority 会接管整个渲染循环。

2. **关闭开关不复原骨骼。** IK 直接改骨骼，关掉后没人还原，
   角色**冻结在上一次 IK 解出的姿势**（手仍粘在剑柄上，看起来像开关没用）。
   现保存 IK 前的局部四元数/位移，关闭时写回。

## 二十、注释契约漂移审计（29 条，含 2 条让功能完全失效）

以 bridgeClient 那条已证实的偏差为样板，通读 8 个区域（agent / viewport / weapon / ik /
gaits / previs / stores），找出「注释声明的行为」与「实际实现」不一致处。

### 高危（功能不生效）

**H1 `collision.ts:565` 椅面高度用错参考系 → 「坐椅子」必报穿模**
`segmentInPropSpace` 的局部系原点在**盒中心**（`position.y + h/2`），
但 chair 分支按底面系写 `0.48h + 0.04`，漏减 `h/2`。同函数 sofa 分支的 `h*0.08`
正是 `0.58h − 0.5h`（中心系），自证坐标系 —— 只有 chair 错。
h=0.9m 时算出局部 0.472（世界 0.922m）而真实座面 0.472m，容差仅 radius≈0.13 → 恒 false。
**一处减法**：`0.48h + 0.04 − 0.5h`。

**H2 `materialStore.ts:109` 守卫键漏掉 overrides → 整个 PBR 面板失效**
`appliedKey` 只存 `scene.uuid`，而 `setOverride`/`setTexture` 不重置它；
`MaterialPanel` 的 effect 依赖 `overrides` 会重新调 `applyTo` → 撞上早退。
**上一轮交付的「PBR 材质面板已完成」实际上第一次改动之后就完全不生效。**
改为指纹 `scene.uuid + JSON.stringify(overrides)`。

**H3 `toolCatalog.ts` `set_camera_keyframe` 契约 100% 不可用**
目录写 `operation: add/update/remove`，handler 只收 `upsert|remove`；
且 handler 强制要求的 `position`/`target` 在目录里**完全缺失** → 模型必然 BAD_ARGS。

**H4 防漂移交叉校验本身只校验参数名** —— 取值/类型/必填性全不校验，这是 H3/M1/M2 的根因。

### 中/低危摘要

- **M1** `set_previs_effect` 的 `path`/`bladeSweep` 类型写成 string/boolean，实为二维数组
- **M2** `repair_physics` 的 `kind`/`foot` 取值写错（`ground`、`foot.L` 会被拒）
- **M3** `footLock.contactTolerance` 是死配置，注释虚构的「滞回」不存在
- **M6/M7** 我自己上一轮的注释漂移：`gripSolve` 声称「本轮不解决腕部定向」但同文件已实现；
  `applyHeldGrip` 声称「必须接进播放循环」但生产路径走 `SwordGripRuntime`，诊断数据永不更新
- **L8** handler 读取但目录未声明的参数：`inspect_skeleton.query`、
  `generate_motion.interpretation`/`duration`、`apply_ik.targetDelta`（共 4 处）

## 二十一、走路曲率：从直线推进到路径驱动

### 问题核实

原通用走路的根位移是 `restPosition[2] + walkedZ + distance * progress`
—— **z 方向纯直线，x 恒定**。另一分支（有道具交互）虽用 `samplePolyline` 走折线，
但**只移动髋骨、不给朝向**，所以身体不转。两条路都产不出「真人走弧线」。

### 三层设计

**1. 按弧长而非按参数采样**（`src/core/motion/path.ts`）
折线各段不等长时按参数 t 插值会产生速度脉动（转弯处「刹车再冲」）。
真人走弧线是匀速沿路径的，故必须按累积弧长取样。

**2. 朝向必须平滑（实测发现的缺陷）**
折线上每段切线是常量，航点处朝向**突变** —— 走起来是「机器人拐直角」。
真人在弧线上身体朝向连续变化：进弯前就开始偏，出弯后才回正。
做法：在 `d ± 0.45m` 弧长窗口内对各段切线按重叠长度加权平均。
**位置仍精确落在折线上，只平滑朝向** —— 不改变脚该踩在哪。

**3. 结构化入口，两种结构都支持**（按要求「都做」）
- `PlanSegment.bow`（弦高比例，0=直线）
- `PlanSegment.viaPoints`（显式途经点，给了就走折线）
- 不传时从 `clause` 推断（`bowFromClause`）

**故意不给默认弧度**：真人走弧线几乎总是因为有东西要绕或中途转向。
「从 A 走到 B」物理上就该是直线，强行加弧是编造动作。
识别规则：绕开/绕过/避开 → 0.18；弧线/拐弯/弯曲 → 0.12；其余 → 0。

### 实测结果

| 走法 | 髋部 max\|yaw\| |
|---|---|
| 走到桌前（直线） | **6.00°**（全是原有骨盆摆动，非路径贡献） |
| 走弧线过去（bow 0.12） | **19.50°** |
| 绕开桌子走到窗前（bow 0.18） | **25.80°** |

弯行时 x 不再恒为 0；直线走法保持逐位不变（向后兼容，既有 march 测试全绿）。

### 过程中我自己犯的三个错（都被实测抓到）

1. **bow=0 时丢了 `walkedZ + distance`** → 角色原地踏步、步频算成 0。
   既有测试立即失败（z 期望 >0.6 实得 0）才暴露。路线端点必须用绝对坐标。
2. **单位混乱**：`marchYaw` 存弧度却在叠加时当度又乘一次 `D2R`，
   路径朝向被压成 1/57。表现是三种走法 `max|yaw|` 全是 6.00°（完全没变化）。
3. **`marchYawKeys.push` 被清理代码时一并删掉**，朝向从未进入轨道。
   我第一个「产生非零偏航」的测试**因为原有骨盆摆动 6° 而误判通过** ——
   理由是错的。靠「三种走法 yaw 完全相同」这个异常才定位到。

**教训**：断言阈值必须区分「本来就有的量」和「我新引入的量」。
用一个与新功能无关的既有振荡去满足新断言，是自欺。

### 已知边界

- 只做了**朝向**，没做**躯干先行**：真人转弯时躯干会先于脚步转向，
  脚也有侧向落点。当前是整躯干随根节点一起转。
- 曲线段**速度不减速**。真实转弯会减速（弯道内侧步幅变短），
  当前速度恒定 —— 只有曲率可用时才有意义，需接步态相位。
- 交互分支（`approachPath` 折线）仍只移动髋骨、未接朝向。

## 二十二、走路的三项补全：躯干先行 / 弯道减速 / 交互分支朝向

### 1. 躯干与视线先行于脚步

真人转弯不是整个身体同时转：躯干（尤其胸廓与头）先于脚步预置。
模型：**躯干朝向 = 根节点在 0.22m 之后（头部 0.44m）的朝向**。

**符号推导时先写反了，被测试抓到。** 朝向本身已被平滑
（`headingAt(d)` 是 `[d−0.45, d+0.45]` 窗口内切线的加权平均），
这个对称窗口**已经**含前瞻成分。要让躯干更领先，必须采样**更前方**。
反向取值时实测拐点后 0.05m 处躯干 0.424 rad < 根节点 0.946 rad —— 躯干「落后」30°。

实测（经两途经点的路径）：`|chest − hips|` 最大 **74.2°**；
直线走法基线 **12.0°**（来自 march 模板原有的骨盆/胸廓反向扭转，
`chest: [0, −pelvisYaw, 0]` 对 `hips: [0, +pelvisYaw, 0]` —— 那是真人走路的辨识特征，不是缺陷）。

### 2. 弯道减速

真人转弯会减速（弯道内侧步幅变短、步频下降）。之前速度恒定。

`curveSpeedFactor(k)`：以最小可行半径 0.5m 归一，直线 1.0 → 极限弯 0.45。

| 曲率 | 半径 | 速度系数 |
|---|---|---|
| 0 | ∞ | 1.000 |
| 0.5 | 2.0m | 0.914 |
| 1.0 | 1.0m | 0.828 |
| 2.0 | 0.5m | 0.656 |
| 3.16 | 0.32m | **0.456** |
| 4.0 | 0.25m | 0.450（下限） |

实现：按速度系数**拉长步态周期** —— 同样时间里步数变少、步幅不变，
这正是过弯的表现（不是滑过去，也不是原地踏步）。

**`pathCurvature` 曾对缓弧和尖角一律返回 0**，减速完全没生效。
错在 `i0 = idx−1 / i1 = idx+1` 后判 `i0 === i1` 提前返回 ——
三点路径的拐点恰好命中该守卫。已加回归测试锁住
（`pathCurvature` 与 `maxPathCurvature` 在拐点处必须一致）。

### 3. 步态采样早于位置循环（又一处时序陷阱）

曲率表在**位置循环**里逐点写入，而步态采样循环在其**之前** ——
查表时表还是空的，减速完全不生效（实测尖角路径与直线路径的步态周期数 **16 vs 16**，完全无差别）。

改为**预计算**：在步态采样之前算出整段路径与曲率剖面，
并抽出 `marchProgressAt` / `marchSampleAt` 作为**唯一**的进度→路径采样入口，
供预计算与位置循环共用（避免两处逻辑分叉）。

### 4. 交互分支也接上朝向

原交互分支用 `samplePolyline(route, smooth)` 走折线，但只移动髋骨、不给朝向 ——
绕开道具时身体不转，看起来像「滑过去」。现与通用分支同一套逻辑（弧长采样 + 朝向 + 减速）。
`samplePolyline` 因此成为死代码，已删除。
